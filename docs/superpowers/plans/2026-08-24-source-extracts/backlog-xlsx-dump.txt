=== SHEET: Read Me ===
Secure Home Router — Product Backlog
Scrum backlog: Epics, User Stories, Tasks, and Non-Functional Requirements

How this workbook is organized:
  • Epics — the 18 major capability areas of the product, spanning user-facing features and the engineering foundation they run on.
  • User Stories — the backlog, one row per story, with acceptance criteria, MoSCoW priority, story points, and mode.
  • Tasks — implementation breakdown (Design/Build/Test) per user story, ready to import into a sprint board.
  • Non-Functional Requirements — cross-cutting quality requirements (usability, accessibility, security, performance, reliability, architecture).

Design principle behind every story: Basic mode is the default experience for non-technical users (big actions,
plain language, one-tap fixes). Advanced mode is opt-in, for power users who want technical control — it never
replaces the Basic default. Infra stories are engineering foundation work with no direct end-user surface.

Priority key (MoSCoW): Must = required for its release · Should = important, not release-blocking · Could = nice to have.
Release key: MVP = first sellable launch (smallest product proving the core thesis) · v1.1 = first post-launch release
(remote access, ad block, guest, multi-router) · v1.2 = Advanced mode & power-user features. Priorities apply WITHIN a
release — a v1.1 'Must' is required for v1.1, not for launch. See the Release Plan sheet for the phased execution order.
Story points: rough relative sizing (Fibonacci: 1,2,3,5,8,13) — re-estimate with your team before committing.
Mode key: Basic = default non-technical experience · Advanced = power-user/opt-in · Both = present in both, adapted per mode ·
Infra = engineering/platform foundation work (no direct end-user UI).

CONFIRMED PRODUCT DECISIONS (locked in, reflected throughout the backlog):
  1. Account & setup flow: LOCAL-FIRST, CLOUD-SECOND. Router is fully secured and usable on the local network with
     zero internet/account required (Epic E14). Cloud account is optional, created whenever internet becomes
     available, and unlocks remote access + multi-router management. Local and cloud identities are architecturally
     independent — losing one never locks out the other.
  2. Existing local configuration is always preserved when a cloud account is created/linked, never reset
     automatically. A full reset is a separate, explicit, user-confirmed action only (US14.4).
  3. Every router ships with a unique, per-unit default admin password (not a shared factory default), and the
     default must be changed before setup can complete, with no skip option (US1.1, US14.2).
  4. Routers are named by the user and support multiple routers under one account (e.g., two homes), each with
     fully isolated devices/settings (Epic E14).
  5. MFA default method is SMS/mobile push. At least one offline-capable method (authenticator app or backup
     codes) must also be enrolled and is verified entirely locally by the router — the user is never fully
     dependent on internet connectivity to log in (Epic E13, US1.2, US3.3).
  6. The block page (for blocked sites/apps) uses a friendly tone with NO self-serve 'request access' option;
     unblocking is a deliberate action only the admin can take from the app (US5.2).
  7. Remote VPN access (Epic E7) provides both live visibility AND control actions remotely — never a read-only
     or action-only subset. Two access scopes coexist: management-only (default) and full home-network access
     (advanced, opt-in) — enabling one does not remove the other.
  8. Base platform: OpenWrt (custom-built image, not stock OpenWrt+LuCI). Chosen over DD-WRT for clean GPL
     licensing with no commercial-license dependency, broader/faster current-hardware support, and its fit as a
     build platform for a distinct commercial product rather than a fixed hobbyist feature bundle (Epic E15).
  9. Firmware updates ship via RAUC (A/B partitions, signed bundles, auto-rollback), and remote access runs over
     an outbound-only WireGuard tunnel (Headscale vs. custom orchestration to be settled via spike US17.1) —
     both chosen specifically because they stay compatible with a future TR-069/TR-369 ISP integration without
     requiring rework (Epics E16, E17).
  10. TECHNICAL REVIEW OUTCOMES (this revision): MVP re-scoped to the smallest sellable product — remote access,
     ad blocking, guest network, multi-router, and all Advanced-mode features moved to v1.1/v1.2 (see Release
     column + Release Plan sheet). Hardware & Manufacturing added as a parallel workstream (E19) — it is the
     likely critical path. External security audit + privacy compliance added as launch-blocking (E20). Mobile
     APP blocking downgraded from a promised feature to a feasibility spike (US5.5) — site/category blocking
     (US5.1) is the reliable, committed capability; per-app blocking (US5.6) is scoped only after the spike.

OPEN BUSINESS DECISION (decide before cloud architecture finalizes): hardware-only revenue vs. hardware +
subscription. Content-filter category databases, the remote-access relay, push infrastructure, and lifetime
security patching are all ongoing per-user costs. Most competitors charge a subscription for exactly these.
This decision caps what the cloud architecture can afford and what marketing can promise — make it in Phase 0.

Future scope note: centralized/ISP remote management (TR-069/TR-369-style) is intentionally NOT included in this
backlog. See the separate document 'future-consideration-isp-centralized-management.md' for architectural notes
to keep in mind now so that project doesn't require a rework later.

=== SHEET: Epics ===
Epic ID | Epic Name | Goal
E1 | Account Setup & Onboarding | Get a non-technical user from unboxing to a secured, working network in one guided flow.
E2 | Security Dashboard (Home) | Give the user a single, plain-language view of their network's security status with one-tap fixes.
E3 | Multi-Factor Authentication | Protect the admin account with flexible, easy-to-set-up MFA (SMS/push, email, authenticator app).
E4 | Device Management & Visibility | Let users see and control every device on their network without technical detail.
E5 | Website / App Blocking & Block Page | Let admins block sites, apps, and mobile apps, with a clear, friendly block page.
E6 | Ad Blocking | Network-wide ad blocking with a simple on/off default and advanced list management for power users.
E7 | Remote Access VPN | Let the user securely connect back into their home network from outside (mobile app, web, or computer) to both view live status and control the router/network as if they were home. Supports two access scopes: management-only (default) and full home-network access (advanced, opt-in).
E8 | Parental Controls | Profile-based, network-level controls for content, time, and scheduling that can't be bypassed by removing an app.
E9 | Guest Network | One-tap guest Wi-Fi that's isolated from the main network.
E10 | Alerts & Notifications | Proactive, friendly alerts so users don't have to remember to check anything.
E11 | Firmware & Auto-Updates | Keep the router secure by default via automatic updates, with manual control for advanced users.
E12 | Advanced / Power User Settings | A separate space for technical settings that doesn't clutter the default experience.
E13 | Offline & No-Internet Access | Guarantee the user can always get into their own router from the local network, even when the router has no internet connection — including a working MFA path that doesn't depend on connectivity.
E14 | Account Creation & Multi-Router Management | Local-first setup (no account or internet required) with an optional cloud account layered on top for remote features and managing multiple named routers (e.g., across two homes) from one login.
E15 | On-Router Software Foundation | Build the custom OpenWrt image and the on-device daemon/API that everything else in this backlog runs on top of.
E16 | Firmware Build & OTA Update Pipeline | Engineering infrastructure for atomic, signed, rollback-capable firmware updates and safe staged rollout to the fleet.
E17 | Remote Access Relay Infrastructure | The outbound-only WireGuard tunnel and relay layer that makes Epic E7's remote access features technically possible, including ACL-based scope enforcement.
E18 | Frontend Platform Foundation | The shared technical foundation (frameworks, API client, component base) that the mobile app and web dashboard are built on.
E19 | Hardware & Manufacturing | The physical product workstream: SoC selection, factory provisioning, regulatory certification, and pilot production. Runs in parallel with software from day one — likely the critical path.
E20 | Security Assurance & Privacy Compliance | Launch-blocking security validation (external audit, disclosure process) and privacy compliance for sensitive data — especially children's activity data. A security product cannot launch without these.
E21 | Support & Diagnostics | Tooling so non-technical customers can get help: self-service troubleshooting and consent-based remote diagnostics for the support team.

=== SHEET: Non-Functional Requirements ===
Category | Requirement
Usability | Common actions (pause internet, block device, check status) completable in under 30 seconds by a non-technical user.
Usability | No default-view screen uses networking jargon (e.g., SSID, WPA, DHCP) without a plain-language label.
Accessibility | App and web dashboard meet WCAG 2.1 AA contrast and screen-reader support.
Accessibility | Dark mode and high-contrast mode available in settings.
Performance | Dashboard loads and shows current security status within 2 seconds on a standard home connection.
Performance | Device list supports 30+ devices without noticeable lag.
Security | All admin credentials and MFA secrets stored encrypted at rest.
Security | All app-to-router and app-to-cloud traffic encrypted in transit (TLS 1.2+).
Security | Default admin password is unique per unit, not a shared factory default.
Compatibility | Native apps for iOS and Android; responsive web dashboard for desktop management.
Compatibility | MFA authenticator support is standards-based (TOTP), not locked to one provider.
Reliability | Core local functions (Wi-Fi, device pause, block page) continue to work if cloud connectivity is temporarily lost.
Localization | UI text externalized for translation; supports at least the primary target market language at launch.
Onboarding | First-run setup enforces password change and offers MFA setup before granting full dashboard access.
Security | Remote access sessions (mobile, web) always require MFA re-authentication, even if the local network does not.
Security | Remote management traffic is end-to-end encrypted via the VPN tunnel; no remote feature relies on an open inbound port on the router.
Security | Remote sessions expire after a defined inactivity period and are individually revocable by the admin.
Reliability | At least one enrolled MFA method (authenticator app or backup codes) must always be verifiable locally by the router without any internet connection — the user is never fully dependent on WAN connectivity to log in.
Reliability | Local (LAN-based) router management continues to function fully during a WAN/internet outage; only genuinely cloud-dependent features degrade, and they do so visibly rather than silently.
Security | Local admin identity (device credentials, TOTP, backup codes) and cloud account identity are architecturally independent — loss of one never locks the user out of the other.
Usability | No user flow requires a factory reset as a side effect of an unrelated action (e.g., creating a cloud account); resets are always a separate, explicit, confirmed action.
Architecture | The on-device daemon is the sole interface between OpenWrt internals (ubus/UCI) and any client application; no frontend code accesses OpenWrt internals directly.
Architecture | All router-initiated cloud/relay connections are outbound-only; the router never accepts inbound connections from the public internet.
Architecture | Firmware updates are delivered as signed, atomic, rollback-capable bundles (RAUC A/B) regardless of who or what triggers them, so this mechanism does not need to change when centralized/ISP management is added later.
