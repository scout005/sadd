# Real OpenWrt Integration — Design & Roadmap

## Goal

Drive as much of this prototype as genuinely can be by a real, running OpenWrt instance, instead of hardcoded demo data. The full target is documented below as a roadmap of "waves," each one a self-contained slice that gets its own implementation plan when its turn comes. **Wave 1** (done) covers two screens on the desktop prototype (`sadd-website.html`): **Devices** and **Firewall & Port Forwarding**. **Wave 2** (done) covers **About**'s version row and **Diagnostics & Logs**' "Recent activity" list. **Wave 3** (done) covers **Settings**' "Wi-Fi name & password"/"Guest network" row values and **Guest Wi-Fi**'s on/off toggle. **Wave 4** (done) covers **Ad Blocking**'s toggle + real blocked-count and **Network & VLANs**' VLAN list. **Wave 5** (done) covers **Developer & API Access**' SSH-key-rotation button, **VPN Server (WireGuard)**'s hero toggle + connection details, and **Per-Device Controls**' real per-MAC "Pause internet" action, reached for the first time via real device navigation from the Devices list. **Wave 6** (done) extends Wave 5's own WireGuard server with real client-peer management (**VPN Server (WireGuard)**'s Client devices list + Add client) and adds real per-device traffic marking (**Traffic & QoS**'s Priority devices list + Add priority device). **Wave 7** (done) makes **Per-Device Controls**' "Bedtime" toggle real — a genuine recurring cron-driven schedule, not the profile-level feature Wave 5 originally (and incorrectly) assumed it required. **Wave 8** (in progress) extends Ad Blocking's own DNS mechanism onto the still-untouched **Parental Controls** hub — a real "Safe Search" toggle and real "Custom blocked sites," both network-wide, honestly disclosed as such. Everything below Wave 8 in the roadmap (renamed **Wave 9**) is sequenced but not yet detailed at the same level; each wave gets its own design pass (reusing this document's architecture) immediately before it's built, since exact implementation details depend on what's actually true inside the running container by that point.

Not every screen in the app can be "real" in this sense — see **Full roadmap** below for the honest breakdown of which screens are genuinely OpenWrt-backable, which are pure UI-flow/marketing content with nothing to execute, and which are cloud/account-system features that would need an entirely different (non-router) backend.

This is a genuinely different kind of work than the rest of this repo's session history (which has been static HTML/CSS/JS editing). It involves real infrastructure (Docker, a real OpenWrt image, real `uci`/`ubus`/`nft` commands) and carries real uncertainty about exact package availability and behavior inside a containerized OpenWrt — some implementation details below are best-effort and may need to change once we're hands-on inside a running container. That's expected and fine for a pilot.

## Why this shape, not a docker-exec shim or raw ubus-from-browser

Two other approaches were considered and rejected:

- **Raw ubus/uci JSON-RPC called directly from the browser** (what LuCI itself effectively does) — technically the most "native" option, but ubus/uci's config schema is low-level OpenWrt internals, not a stable public contract. Building a product UI directly against it means a future OpenWrt version bump can silently break the frontend.
- **An external shim that `docker exec`s into the container** — fast to build, but a dead end for production: on real router hardware there is no outside host to exec into. Anything built this way is throwaway testing scaffolding, not a step toward a real product.

Instead: a small API daemon lives **inside the OpenWrt image itself**, under `uhttpd` (the same web server LuCI uses), written in Lua (OpenWrt's native scripting layer for this, `uhttpd`'s Lua/CGI handler support) or, as a fallback if Lua tooling proves too fragile inside the pilot image, a cross-compiled Go binary serving the same contract. This daemon exposes a small, clean, versioned REST API and is the only thing that shells out to `uci`/`ubus`/`nft`. The frontend never touches OpenWrt internals directly. Crucially, this exact code can run unmodified on real router hardware later — nothing here is thrown away when moving from Docker testing to a real device.

## Architecture

```
Browser (sadd-website.html — Wave 1: devices + advfirewall screens; Wave 2: about's version row + advlogs' Recent Activity list; Wave 3: settings' Wi-Fi/guest rows + guest's on/off toggle; Wave 4: adblock's stat/switch + advnetwork's VLAN list; Wave 5: advapi's Rotate SSH key button, advwireguard's hero toggle + connection details, devcontrols' real per-MAC Pause internet action reached via real Devices navigation; Wave 6: advwireguard's Client devices list + Add client + per-client toggle, advqos's Priority devices list + Add priority device; Wave 7: devcontrols' real per-MAC Bedtime recurring-schedule toggle, a second real write control on the same screen Wave 5 already made real)
        │  same-origin fetch('/api/...')
        ▼
uhttpd  (inside the OpenWrt container, also serves the static HTML file)
        │  routes /api/* to
        ▼
Lua API daemon (or Go fallback)
        │  shells out to
        ▼
uci / ubus / nft   (real OpenWrt config + firewall state)
        │
        ▼
Real kernel netfilter (nftables) + real dnsmasq DHCP leases,
inside the Docker container's network namespace
```

The container is started with `--cap-add=NET_ADMIN --cap-add=NET_RAW` (required for `nft` rule manipulation) and attached to two Docker networks — one standing in for "WAN," one for "LAN" — so `uci network`/`uci firewall` have two real zones to bind to, mirroring a real router's topology instead of one flat container network.

### 2. Devices API
- `GET /cgi-bin/api/devices` → reads real DHCP lease data from `/tmp/dhcp.leases` (confirmed dnsmasq's real format, not `ubus call dhcp` — that ubus object is served by `odhcpd`, which never sees dnsmasq's IPv4 leases in this environment, confirmed `docker/facts.md` §2a) plus a liveness signal from `/proc/net/arp`, keyed by each lease's own IP (not MAC — a MAC-keyed version was shipped, found to false-positive, and fixed, `docker/facts.md` §1a). Returns `[{hostname, ip, mac, leaseExpires, online}, ...]`.
- Read-only, exactly as planned — no device-blocking/quarantine actions.

### 3. Firewall & Port Forwarding API
- `GET /cgi-bin/api/firewall-rules` → reads current `uci show firewall` `redirect` sections, returns them as JSON with a stable generated id (`uci rename`d immediately after `uci add`, per `docker/facts.md` §4's warning that anonymous sections shift index on deletion).
- `POST /cgi-bin/api/firewall-rules` → adds a new redirect section (hardcoded `src='wan'`, matching real port-forward semantics), verifies each write before committing, rolls back (`uci revert firewall`) on any partial failure, then reloads `fw4` so the change is live immediately.
- `DELETE /cgi-bin/api/firewall-rules?id=<id>` → removes the section (query param, not a path segment — see `docker/facts.md` §10 for how uhttpd exposes this to CGI), commits, reloads.
- **No auth of any kind** beyond what SSH/uhttpd already require to reach the VM at all — see the new Security note below.

### WireGuard API (Wave 5)
- `GET /cgi-bin/api/wireguard` → `{"running", "port", "publicKey", "subnet"}`. `running` comes from `ubus call network.interface.wg0 status` (the same kernel-liveness idea `/api/vlans`'s `ip link show` check uses); `port`/`publicKey` are always read live from `wg show wg0` (never from uci, which only ever stores the *private* key), falling back to the provisioned port and an empty key when `wg0` doesn't exist (e.g. mid-toggle-off); `subnet` is the one baseline value provisioning always sets (`10.9.0.0/24`), not yet user-editable through this screen.
- `POST /cgi-bin/api/wireguard` with `{"enabled": <bool>}` → writes `network.wg0.disabled` and runs `ifup`/`ifdown wg0`, same write-then-readback-verify-then-commit-or-revert discipline as `wifi`/`adblock`'s POST handlers. Both directions confirmed live: `enabled:false` makes `ip link show wg0` genuinely report "can't find device"; `enabled:true` brings the real interface back with the same public key (the private key persists in `/etc/wireguard-privkey` regardless of the toggle).
- Provisioning (`docker/provision/11-provision-wireguard-api.sh`) installs a real 9-package kmod dependency chain plus `wireguard-tools` (host-download-then-scp, same no-outbound-internet workaround as every opkg install in this project) and brings up a real, persisted `wg0` interface before this endpoint is ever deployed — see `docker/README.md`'s step 11 for the full idempotent/self-healing provisioning detail.

### SSH Key API (Wave 5)
- `POST /cgi-bin/api/ssh-key` (no request body) → deletes both dropbear host key files and restarts dropbear, which auto-regenerates them; returns `{"ok":true,"fingerprint":"SHA256:..."}` for the new RSA key (read back via `dropbearkey -y -f ... | grep Fingerprint` after a defensive `sleep 1`), or `Status: 500` with `{"ok":false,"error":...}` if the fingerprint can't be read back. Any method other than `POST` gets `Status: 405`.
- Confirmed live to genuinely rotate the real key on every call, not toggle between two fixed values (a second POST changes the fingerprint again to a third distinct value) — see `docker/README.md`'s step 12 curl example for the exact live-verified sequence.
- Safe for this project's own SSH-based verification workflow specifically because every SSH connection this project makes passes `-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null` — there's no persisted `known_hosts` entry anywhere to conflict with a rotated key. A real deployment using normal host-key pinning would need to separately warn the operator about the resulting "host key changed" client prompt; that operator-facing warning is out of scope here (see Known Limitations in `docker/README.md`).

### Device Pause API (Wave 5)
- `GET /cgi-bin/api/device-pause?mac=<mac>` → `{"paused": <bool>, "remainingSeconds": <int>}`, read-only, discloses whether a specific MAC currently has an active pause and how much longer it has.
- `POST /cgi-bin/api/device-pause` with `{"mac": "<mac>", "minutes": <int, 1-1440>}` → creates or REPLACES a real `uci firewall` `rule` section (`src='lan'`, `src_mac=<mac>`, `dest='wan'`, `target='REJECT'`, plus a custom `paused_until` epoch-seconds option) — `dest='wan'` is required to land the rule in the `forward_lan` chain as a real reject of the device's outbound traffic, not just `input_lan` (traffic addressed to the router itself), confirmed live in `docker/facts.md` §14. Same stable-id-rename-before-any-further-read/write and write-then-readback-verify-then-commit-or-revert discipline as `firewall-rules`/`vlans`.
- Auto-expiry is handled out-of-band by a separate cron-driven sweep (`docker/provision/lib/devpause-sweep.sh`, deployed and seeded into `/etc/crontabs/root` by `docker/provision/13-provision-devpause-api.sh`, running every 60 seconds) — this endpoint only ever creates/replaces/reads a pause rule, it never deletes an expired one itself. The sweep re-scans `uci show firewall` fresh before every single deletion (not a stale upfront batch) specifically so multiple same-tick expiries each address the correct section despite anonymous-section renumbering on delete — proven live for both a single expiry and a genuine three-simultaneous-expiry scenario (see `docker/README.md`'s file note for the exact live proof, including matching `logread` lines from the same cron invocation).
- The rule itself is real, correct `uci`/`fw4` config, but — like every other WAN-dependent feature in this project — isn't end-to-end packet-testable in this VM's topology (no real WAN interface); see the Testing section's Wave 5 update below.

### WireGuard Clients API (Wave 6)
- `GET /cgi-bin/api/wireguard-clients` → `[{"id", "name", "publicKey", "enabled", "added"}, ...]`, one entry per real `wireguard_wg0` uci peer section on `wg0` — extends Wave 5's own WireGuard server with real client-peer management for the VPN Server screen's "Client devices" list.
- `POST /cgi-bin/api/wireguard-clients`, dispatched by request shape: a body with `name` creates a new client — a real keypair (`wg genkey`/`wg pubkey`), the next unused `/32` in `10.9.0.2`-`10.9.0.254` (scanned from existing peers' `allowed_ips`), and a new `wireguard_wg0` peer section, stable-id-renamed the same way `firewall-rules`/`device-pause`/`vlans` already do (`wgc_<time>_<6 hex>`); the response returns the client's full WireGuard config text, private key included — **the private key is returned exactly once and never written to uci, logged, or retrievable again afterward**, matching real WireGuard practice (the server only ever needs a peer's *public* key). A body with `id`+`enabled` instead toggles that peer's `disabled` uci option and runs `ifdown wg0; ifup wg0`, confirmed live to genuinely add/remove the peer from `wg show wg0`'s own output in both directions. No `DELETE` — same read-mostly-list choice `/api/vlans` made; a client created here can currently only be removed by hand over SSH.
- **A real command-injection vulnerability was found and fixed here during code review (commit `cfbb97d`), not merely a hypothetical hardening exercise:** the toggle path's client-supplied `id` is concatenated directly into `uci get`/`uci set` command strings — `shell_quote()` in this codebase only ever escapes option *values*, not a section-id position in the command itself — and the first version of this endpoint accepted any non-empty string `id` with no further check, meaning a crafted `id` could execute arbitrary shell commands on the VM. Fixed by rejecting any `id` containing a character outside `[A-Za-z0-9_]` *before* it is ever concatenated into a uci command, mirroring the `[%w_]+`-only precedent `firewall-rules`' `DELETE` handler already established for the only other client-supplied section id in this codebase. Confirmed live post-fix: `id` values containing `;`, backticks, and `$()` are rejected with a clean `400` before any uci call runs. Full detail in `docker/README.md`'s file note for `docker/provision/www/api/wireguard-clients`.

### QoS Priority API (Wave 6)
- `GET /cgi-bin/api/qos-priority` → `[{"mac"}, ...]`, one entry per real `uci firewall` `rule` section marking a device's traffic for priority. Only `mac` is stored server-side; the frontend cross-references a fresh `/api/devices` fetch by MAC at render time to show a display name, falling back to the raw MAC for a device that isn't currently DHCP-leased.
- `POST /cgi-bin/api/qos-priority` with `{"mac": "<mac>"}` → creates a real `rule` section (`src='lan'`, `src_mac=<mac>`, `dest='wan'`, `target='MARK'`, `set_mark='0x2a'`), confirmed live to land in the real `mangle_forward` nft chain and genuinely mark the device's own forwarded traffic (not just traffic addressed to the router itself) — the same `src=lan`/`dest=wan` distinction Wave 5's device-pause `REJECT` rule already established, applying identically here for `MARK`. Idempotent per MAC: a second `POST` for an already-marked device is a no-op success, not a duplicate rule. Same stable-id-rename, write-then-readback-verify-then-commit-or-revert discipline, and strict MAC validation as `device-pause`. No `DELETE` — same choice `/api/vlans` made; a rule created here can currently only be removed by hand over SSH.
- Unlike `wireguard-clients`, this endpoint never accepts a client-supplied section id at all — both the rule's `.name` and its stable renamed id are derived internally from `mac`, which is strictly regex-validated before it ever touches a uci command — built with Wave 6's own `wireguard-clients` command-injection finding already in hand, deliberately closing off the same class of bug at the design level rather than only by input validation. Confirmed live: MAC-shaped payloads containing `;`, backticks, and `$()` are all rejected with a clean `400` before any uci call runs, and no injected command executes.
- `0x2a` is a fixed, arbitrary mark value — there is no second priority tier or `tc`/SQM queueing discipline consuming it yet in this wave, so marking a device currently has no measurable effect on its traffic's latency or bandwidth; see Known Limitations in `docker/README.md`. Wiring a real consumer for this mark is Wave 9 territory (the same missing piece "Bandwidth used today" needs), not part of this wave's narrower "prove the marking mechanism is real" scope.

### Device Bedtime API (Wave 7)
- `GET /cgi-bin/api/device-bedtime?mac=<mac>` → `{"enabled": <bool>, "active": <bool>}` — `enabled` is whether a Bedtime schedule is configured for this device at all (a `bedtime-<mac>` uci `rule` section exists); `active` is whether it's blocking right now (that section's own `enabled` uci option reads `"1"`); both `false` if no rule exists for this MAC.
- `POST /cgi-bin/api/device-bedtime` with `{"mac": "<mac>", "enabled": true|false}` → creates or removes a real, recurring per-device schedule. `enabled:true` on a MAC with no existing rule creates a `uci firewall` `rule` section reusing the exact `src='lan'`/`dest='wan'`/`target='REJECT'`/`proto='all'` shape Wave 5's device-pause already established (`docker/facts.md` §14), but with a genuinely different enforcement mechanism: instead of a fixed expiry timestamp, the rule's own `enabled` uci option — confirmed live to be honored independently by `fw4` (§16) — is set from the CURRENT UTC hour computed at creation time, so the block takes effect immediately if it's already nighttime, without waiting on the next sweep tick; `enabled:false` removes the rule (idempotent no-op if already absent). Same stable-id-rename, write-then-readback-verify-then-commit-or-revert discipline, strict MAC validation, and canonical `json_escape()` as every other write endpoint in this directory. Never accepts a client-supplied section id, the same by-construction avoidance of `wireguard-clients`' own command-injection bug class `qos-priority` already established.
- Enforcement of the recurring schedule itself is a separate, independently-scheduled cron sweep (`docker/provision/lib/bedtime-sweep.sh`, deployed by `docker/provision/15-provision-bedtime-api.sh`, running every 5 minutes): it reconciles every existing `bedtime-<mac>` rule's `enabled` option to match whether the current UTC hour falls in a fixed 21:00-07:00 window, never creating or deleting a rule itself — the same "sweep only ever adjusts, the endpoint only ever creates/removes" division of labor Wave 5 established for device-pause.
- **Honest, disclosed limitation, not a bug**: this VM has no configured timezone at all (`docker/facts.md` §16: `date` shows UTC, `uci get system.@system[0].zonename` returns "Entry not found"), so "Bedtime" here enforces a fixed UTC 21:00-07:00 window, not any real-world local time — the same category of disclosed approximation as Wave 5's client-side "Until tomorrow" minutes-to-midnight computation.
- **A real cross-process integration risk, found and fixed via code review (commit `d1b7a9c`), not merely a hypothetical hardening exercise:** this endpoint and `bedtime-sweep.sh` legitimately mutate the exact same uci section's `enabled` option from two independently-scheduled processes, and `uci commit firewall` commits the *entire* firewall delta, not just the caller's own change — a sweep tick landing between this endpoint's own readback and its own commit could previously make the create response report a stale value for up to 5 minutes. Fixed by having both the create and delete paths do one final fresh `uci` read *after* their own commit, and report that observed value rather than a pre-commit local. Two further, smaller findings from the same review round: the delete path's `uci -q delete` exit status was previously discarded entirely, making a failed delete indistinguishable from a real removal (fixed with a post-delete readback that returns a real `500` on failure instead of a false `200`); and the endpoint originally omitted `proto` on rule creation, which per `docker/facts.md` §15's own finding for a similarly proto-less rule likely defaults to matching only tcp+udp, silently leaving ICMP unblocked during Bedtime (fixed by setting `proto='all'` explicitly, matching device-pause's own precedent). Full detail in `docker/README.md`'s file note for `docker/provision/www/api/device-bedtime`.
- **A real busybox-ash shell gotcha, found and avoided before it ever shipped, not discovered by a live failure:** `date -u +%H`'s zero-padded output (e.g. `"08"`) breaks `$(( ))` arithmetic expansion via octal misinterpretation on this VM's ash, and ash's usual `10#$HOUR` base-prefix workaround also fails here (confirmed live: `ash: arithmetic syntax error`) — `bedtime-sweep.sh` was written from the start to never wrap `$HOUR` in arithmetic expansion at all, relying on POSIX `test`/`[`'s `-ge`/`-lt` string comparison instead, which handles the zero-padded form correctly with no reinterpretation.

### 5. Security posture (added 2026-08-31 — not in the original design)
`/cgi-bin/api/*` has no authentication of any kind, and `docker-compose.yml`'s `ports: "8081:80"` binds to all interfaces (`0.0.0.0`), not just `localhost` — so anyone who can reach the host machine on the local network can add or delete real firewall rules, flip the real guest Wi-Fi network on/off, flip real DNS ad blocking on/off, flip the real WireGuard server on/off, rotate this VM's real SSH host keys, pause/unpause a real device's internet access, create or toggle a real WireGuard client peer, mark a real device's traffic for priority, or create/remove a real recurring Bedtime schedule for a device (nine independent write endpoints as of Wave 7, verified by each file's own method dispatch, not assumed: Wave 1's `POST/DELETE /cgi-bin/api/firewall-rules`, Wave 3's `POST /cgi-bin/api/wifi`, Wave 4's `POST /cgi-bin/api/adblock`, Wave 5's `POST /cgi-bin/api/wireguard`, `POST /cgi-bin/api/ssh-key`, and `POST /cgi-bin/api/device-pause`, Wave 6's `POST /cgi-bin/api/wireguard-clients` and `POST /cgi-bin/api/qos-priority`, and Wave 7's `POST /cgi-bin/api/device-bedtime`), with a plain `curl`, no login required. `/api/ssh-key` is a little different in kind from the rest — it doesn't mutate any persisted uci config the way they do, but a plain unauthenticated `POST` still immediately rotates real SSH host keys with no confirmation, undo, or operator warning. This is acceptable **only** because this pilot is an explicitly local, single-user dev/test tool with no intended multi-user or untrusted-network exposure (see Non-goals below) — it is not something to carry forward into any later wave or real deployment without addressing. (Wave 6 also found and fixed a genuine command-injection vulnerability in `/api/wireguard-clients`' toggle path, beyond this general lack of authentication — see the Testing section's Wave 6 update below and the WireGuard Clients API subsection above for the full detail. Wave 7's own code-review findings on `/api/device-bedtime` were a different class — a cross-process staleness race and an unverified delete, not injection — see the Testing section's Wave 7 update below and the Device Bedtime API subsection above.)

The same lack of authentication also applies to every **read-only** endpoint (`/api/devices`, `/api/logs`, `/api/system-info`, as of Wave 4 `/api/vlans`, as of Wave 5 `/api/device-pause`'s own `GET`, as of Wave 6 `/api/wireguard-clients`' own `GET` and `/api/qos-priority`'s own `GET`, and as of Wave 7 `/api/device-bedtime`'s own `GET`) — anyone reachable on the local network can silently read real connected-device presence/MAC/IP data, real syslog/dropbear log lines, real distro/hardware/uptime info, real VLAN/network topology, whether a specific MAC currently has an active pause and how much longer it has (Wave 5), real WireGuard client identity/public-key/enabled data, which MACs are currently marked for traffic priority (Wave 6), and whether a specific MAC currently has a Bedtime schedule configured and whether it's actively blocking right now (Wave 7), with a plain `curl`, no login required. This is disclosure rather than mutation, but it's still real information about a real (if virtual) router, and falls under the same acceptable-only-because-local-single-user-dev-tool reasoning above — not something to carry forward as-is either.

### 6. Error handling
If any of the real endpoints backing the eight now-live screen sections (`/cgi-bin/api/devices`, `/cgi-bin/api/firewall-rules`, `/cgi-bin/api/system-info`, `/cgi-bin/api/logs`, `/cgi-bin/api/wifi` GET, `/cgi-bin/api/wifi` POST, `/cgi-bin/api/adblock` GET, `/cgi-bin/api/adblock` POST, `/cgi-bin/api/vlans`) is unreachable (e.g. the file is opened directly via `file://` outside the container, or the container isn't running), the affected screen/section falls back to today's existing static demo data and shows a small, non-blocking notice (wording varies slightly by screen, e.g. "Can't reach router — showing demo data", "...showing default version", "...guest Wi-Fi not changed", "...ad blocking not changed") rather than breaking or blanking the screen. This keeps the rest of the prototype's existing behavior (all other screens, the search feature, etc.) working exactly as before regardless of whether the container is up.

## Non-goals for this pilot

- Real Wi-Fi radios — no physical wireless hardware exists in a container; any "Wi-Fi settings" work later is config-level only (`uci get/set wireless`), not an actually-broadcasting network.

- Any auth/session model beyond a single shared admin session for the pilot — proper multi-user RBAC (matching the product's family-profile model) is a later concern.
- Persisting the container across host reboots, or treating this as a daily-driver setup — it's a dev/test environment.
- Any screen section other than the eight listed in "Frontend changes" above becoming live — everything else keeps working exactly as it does today.

### Environment bring-up: findings from a live investigation (2026-08-30)

Before writing the implementation plan, the boot environment itself was tested hands-on, since this repo already had a `docker/docker-compose.yml` stub. This replaces the original "run `openwrt/rootfs` as a plain userland container" idea below with a much better-grounded plan, and leaves one concrete blocker for Task 1 to resolve:

**Confirmed working:**
- Docker Desktop on this machine has KVM available to containers (`--device=/dev/kvm` works, verified directly).
- The official OpenWrt 23.05.5 x86-64 combined image, once downloaded, is a genuinely valid, bootable raw disk (confirmed via `file` → "DOS/MBR boot sector", and a full real kernel boot reaching a console prompt with `br-lan` up).
- A minimal hand-written `qemu-system-x86_64 -enable-kvm -drive file=...,format=raw ...` container (`docker/Dockerfile.qemu-direct`, committed) successfully boots this real OpenWrt kernel end-to-end. This is a proven fallback path if the options below don't pan out.

**Two real bugs found and worked around:**
1. The official OpenWrt combined `.img.gz` has benign trailing bytes after its valid gzip stream (confirmed: `gzip -dc` still produces a complete, correct, valid disk image; the trailing bytes are just data gzip's strict checker flags as a warning/exit-code-2, not actual corruption). The originally-stubbed `qemux/qemu` wrapper's own extractor treats this as a fatal error and infinite-restart-loops. Fix: pre-decompress once, bind the raw `.img` in directly (this wrapper supports that natively) — bypasses its extractor entirely.
2. Even with a valid pre-extracted raw disk bound in, that same wrapper's own disk-boot logic reports "Boot failed: not a bootable disk" — it appears designed around installer-media workflows (like Windows/macOS ISO installs onto a fresh empty disk) rather than booting a pre-built, already-complete disk image directly. Not resolved with that wrapper; abandoned in favor of the option below.

**Current best candidate, with one known blocker:** `albrechtloh/openwrt-docker` (https://github.com/AlbrechtL/openwrt-docker) is a project purpose-built for exactly this scenario — real OpenWrt kernel, KVM acceleration, and (relevant to this Windows/WSL2/Docker Desktop environment specifically) a documented `LAN_IF: "veth"` mode for exactly the "no direct physical NIC passthrough available" case. Tried directly (compose committed to `docker/docker-compose.yml`) — it correctly detects KVM and starts building its virtual networking, but its container self-discovery step (`nsenter --target 1 --mount docker inspect -f '{{.State.Pid}}' $(cat /etc/hostname)`) fails with `nsenter: failed to execute docker: No such file or directory`. This runs with `pid: "host"`, so `nsenter --target 1` enters the true host PID namespace and tries to exec a `docker` CLI binary there — which exists on a normal bare-metal Linux Docker host, but Docker Desktop's actual host namespace is a minimal purpose-built LinuxKit VM with no such binary. This is a genuine environment-specific incompatibility with Docker Desktop, not a config typo.

**RESOLVED (2026-08-31):** none of the three candidate fixes above panned out for `albrechtloh/openwrt-docker` — mounting `/var/run/docker.sock` didn't help (confirmed: `nsenter --mount` switches into the *host's* actual filesystem, where the container's own bind mounts, socket included, are no longer visible at all), and the project's own issue tracker (#32) confirmed this exact failure mode: on native Linux it was traced to Docker being installed via `snap` (whose confinement hides the `docker` binary from a plain host-namespace `nsenter` the same way), fixed there by switching to a normal apt install — no equivalent fix exists for Docker Desktop, whose host namespace is a minimal LinuxKit VM that was never going to contain a `docker` binary at all. This is a genuine architectural dead end for this project on Docker Desktop specifically, not a missing flag.

Fell back to option 3 — hand-rolled tap networking around the already-proven `docker/Dockerfile.qemu-direct` direct-QEMU path — and it worked on the first properly-configured attempt. Root cause of why plain QEMU usermode/slirp networking (the very first thing tried) couldn't work at all: slirp only forwards to whatever private address *it* assigns the guest (e.g. `10.0.2.15`); OpenWrt's `br-lan` never requests one via DHCP — it self-assigns `192.168.1.1` as a static default regardless of what the network layer offers. A tap device (`tap0`, assigned `192.168.1.2/24` — the same subnet as `br-lan`) makes the guest's own real address a direct L2 neighbor of the container, and a pair of `socat` relays (`container:80 → 192.168.1.1:80`, `container:22 → 192.168.1.1:22`) bridges that to the ports Docker exposes to the host. Verified end-to-end: `curl http://localhost:8081/` returns a real `200` serving genuine LuCI HTML ("LuCI - Lua Configuration Interface"), and the real dropbear SSH banner (`SSH-2.0-dropbear`) is reachable on the mapped SSH port — both through the exact `docker compose up -d` command documented in `docker/README.md`, from a cold start (freshly-fetched `boot.img`, freshly-built image), not just an already-running dev session.

Final setup: `docker/docker-compose.yml` builds `docker/Dockerfile.qemu-direct` (Debian + `qemu-system-x86` + `iproute2` + `socat`), whose `docker/entrypoint.sh` creates the tap device, starts the relays, then execs QEMU. `docker/fetch-boot-image.sh` reproducibly downloads and prepares the disk image (gitignored — not committed, ~120MB). Full details, exact commands, and the two abandoned approaches are in `docker/README.md`.

This replaces the design's earlier assumption of a plain `openwrt/rootfs` userland container — running the *real* OpenWrt kernel under KVM is both more authentic and, as it turned out, the path that actually works.
